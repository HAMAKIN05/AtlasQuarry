# AtlasQuarry 機能定義書 v1.0

> プロジェクト名: **AtlasQuarry**（アトラスクォーリー）／略称 AQ・Quarry
> リポジトリ・作業フォルダ名: `atlasquarry`

> 全未決事項を確定した実装用の版。
> このドキュメントは実装のひな形生成に使用する。

---

## 1. 目的とスコープ

### 1.1 目的

法人内システムの内製化プロジェクトにおいて、以下を単一のツールで完結させる。

- 開発対象と進捗の可視化（開発者・上司・経営者が同じ画面を見る）
- 現場からの要望の受付と、開発タスクへの変換
- 仕様書・ナレッジ・議事録の体系的な蓄積
- AIエージェントを含む「作業者」の稼働管理

### 1.2 前提条件

| 項目 | 決定 |
|---|---|
| 準拠すべき外部基準・社内規程 | なし |
| VPS設置場所の制約 | なし |
| 格納禁止データ | 指定なし |
| 想定利用人数 | 3名（開発者1・上司1・経営者1）＋AIエージェント |
| 開発体制 | 1名 |
| チャット基盤 | Discord（外部委譲） |

### 1.3 スコープ外

| 項目 | 理由 |
|---|---|
| 汎用チャット機能 | Discord に委譲（§7） |
| Discord ↔ ツールの双方向メッセージ同期 | 実装コストが「チャット自作」の7〜8割に達し、外部委譲の意味が消える |
| ソースコード管理 | Git に任せる。連携のみ |
| リアルタイム共同編集 | ドキュメントは排他ロック方式 |
| モバイルネイティブアプリ | レスポンシブ Web + PWA |
| 音声会議・録音・文字起こし | Discord の音声機能＋外部ツールで運用カバー |
| クリティカルパス自動計算 | 依存関係の入力量が少ないため意味が出ない。v1 見送り |
| SSO / LDAP | 3名規模では不要 |

## 2. 用語定義

| DB上の名称 | 画面表示名 | 定義 | 例 |
|---|---|---|---|
| `product` | プロダクト | 内製する個々のシステム | 予約管理システム |
| `feature` | **開発項目** | プロダクト内の機能まとまり。ガントの単位 | 予約キャンセル機能 |
| `task` | タスク | 実作業の最小単位。かんばんのカード | キャンセルAPIの実装 |
| `request` | 要望 | 生の依頼。タスクの前段階 | 電話でもキャンセルできるように |
| `actor` | メンバー | 作業主体。人間とAIエージェントの両方 | 開発者、Claude Code |
| `document` | ドキュメント | 仕様書・ナレッジ・議事録 | 予約API仕様書 |
| `activity` | アクティビティ | 全操作の記録 | Aがタスク#12を完了にした |

**階層**: `プロダクト > 開発項目 > タスク > サブタスク`

`task.feature_id` は **nullable**。バグ修正・雑務など、開発項目にまとめる意味がないタスクは開発項目なしで登録できる。

### 6.2 設計上の要点

**`activity` が3つの機能を兼ねる**

1. 変更履歴（誰がいつ何を変更したか）
2. ヒートマップの濃淡ソース
3. タスク詳細のタイムライン表示

ヒートマップを `work_log` の手入力に依存させると、入力が途切れた日が空白になり、可視化が嘘をつく。自動記録される `activity` を主軸にする。

**`work_log` は工数算出専用**

`work_log` が空でもヒートマップは動く。この分離を崩さない。

**人間とAIを `actor` で統一**

`type` カラムで区別するのみ。分けると担当者・工数・通知・ヒートマップの全機能で分岐が発生する。

**`task.position` は double precision**

かんばんの並び替えで全行 UPDATE しないため。挿入時は前後の中間値を取る。精度が枯渇したら再採番するバッチを用意する。

**`task.product_id` を冗長に持つ**

`feature_id` が null のタスクでも所属プロダクトを辿れるようにするため。

**`integration.config_encrypted` は必ず暗号化**

Discord の Webhook URL は実質的な認証情報。平文保存すると DB バックアップ漏洩時の被害範囲が広がる。ログにも出力しない。

**`decision_note` を独立させる理由**

`/decide` で拾った決定事項を、いきなり議事録本文に書き込まない。バッファに溜め、人間が確認してからマージする。自動追記にすると議事録が雑多になり読まれなくなる。

### 6.3 開発項目の日付・進捗の導出

原則としてタスクから自動導出する。

```
start_date = MIN(task.start_date)   -- 配下タスク
due_date   = MAX(task.due_date)
progress   = 完了タスク数 / 総タスク数
```

`feature.start_date` / `due_date` に値がある場合はそちらを優先（まだタスクを切っていない予定段階の開発項目のため）。

### 6.4 アクティビティの重み

`app_setting` に格納し、運用後に調整可能とする。初期値：

| アクション | 重み |
|---|---|
| タスク完了 | 5 |
| ドキュメント作成・更新 | 3 |
| タスク作成・編集 | 2 |
| 要望のトリアージ | 2 |
| コメント投稿 | 1 |
| ステータス変更 | 1 |

### モバイル対応

S-07 ガントと S-16 工数集計は横スクロール許容。**他はモバイルファーストで設計する。** 特に S-05 かんばんと S-06 タスク詳細は、スマホからのコメント・ステータス変更が主用途になるため最優先。

### エディタ方針

プレーンMarkdown（textarea + プレビュー）。リッチテキストは採用しない。内部表現を Markdown で保持することで、F-19 のエクスポートと版差分表示が単純になる。ツールバーによる入力補助は任意で後付け可。

## 8. Discord 連携

### 8.1 チャンネル構成

```
#general          雑談・連絡
#requests         要望の議論
#notifications    ツールからの通知（Bot専用。人間は書き込まない）
#dev              技術的な議論
```

`#notifications` の分離は必須。通知と会話を混ぜると、通知でスレッドが埋まって会話が読めなくなる。

### 8.2 連携レベル

| Lv | 内容 | 採否 |
|---|---|---|
| 1 | ツール → Discord への通知（一方向） | 採用（F-22a） |
| 2 | タスクごとのスレッド自動生成 | 見送り |
| 3 | 双方向メッセージ同期 | **スコープ外** |
| 4 | Discord から要望を起票 | 採用（F-22c、コマンドのみ） |

### 8.3 Bot の構成

**Bot アプリケーションは1つに集約。常駐（Gateway 接続）は行わない。**

- 通知送信 → Outgoing Webhook（HTTPリクエストのみ）
- コマンド受信 → Interactions Endpoint（HTTPリクエストのみ）

Next.js の Route Handler で受けるため、常駐プロセスが増えない。

### 8.4 スラッシュコマンド

| コマンド | 動作 | フェーズ |
|---|---|---|
| `/request <内容>` | 要望を起票。`source=discord_command` | v0.2 |
| `/decide <内容>` | 決定事項を `decision_note` に登録 | v0.4 |
| `/task <ID>` | タスク概要を返信（本人にのみ表示） | v0.4 |

### 8.5 実装上の注意

**ユーザー紐付け**
`actor_external_id.external_id` に Discord ユーザーID（Snowflake）を保存。**ユーザー名は変更可能なため、名前での紐付けは必ず壊れる。**

**メンション形式**
`<@ユーザーID>` 形式でなければ通知が飛ばない。

**Interactions の署名検証**
Discord からの POST は Ed25519 署名の検証が必須。検証失敗時は 401 を返す。**3秒以内に応答**しないとタイムアウトするため、重い処理は deferred response を返してから非同期で処理する。

**レート制限と非同期化**
Discord API はおよそ 5リクエスト/秒。一括操作（例: 20タスクの一括クローズ）で瞬間的に超える可能性がある。**通知は `notification_queue` に入れて非同期送信する。** 同期送信にすると Discord 側が詰まったときツール本体のレスポンスが停止する。

**Webhook URL の保護**
`integration.config_encrypted` に暗号化保存。ログに出力しない。

### 8.6 通知アダプタ層

```
ドメインイベント → EventBus → notification_queue → NotifierAdapter
                                                     ├ DiscordNotifier
                                                     ├ MailNotifier
                                                     └ (将来) 他サービス
```

特定サービスへの密結合を避ける。アダプタ層の実装コストは半日程度、乗り換え時の書き直しは数日〜1週間。

### 8.7 通知イベントと既定値

| イベント | 既定の通知先 |
|---|---|
| 自分にタスクが割り当てられた | Web + Discord |
| 自分のタスクにコメントが付いた | Web + Discord |
| メンションされた | Web + Discord + メール |
| 要望が新規登録された | Web + Discord |
| 要望が採用/却下された | Web + Discord |
| 期限が明日に迫った | Web + メール |
| 期限を超過した | Web + Discord + メール |
| エージェントが作業を完了した | Web |

メールは Discord のプッシュ通知が届かない場合の保険。重要度の高いイベントは二重化する。

## 9. 議事録の扱い

### 9.1 基本方針

**チャットログは議事録ではない。** Discord に残るのは議論の過程であり、決定事項ではない。両者を分けて保存する。

```
議論 → Discord に流れる
  ↓ 決定した時点で
決定 → document (type=minutes) に転記
  ↓ 実行が必要なら
作業 → task として起票
```

転記の手間は意図的に残す。転記時に「結局何が決まったのか」を言語化する必要があるため、曖昧な合意が炙り出される。全自動同期にするとこの効果が失われる。

### 9.2 転記コストの低減（段階的）

| 手段 | 実装コスト | フェーズ |
|---|---|---|
| 議事録ドキュメントの手動作成 | − | v0.3 |
| `/decide` で決定事項をバッファに登録 | 1日 | v0.4 |
| 議事録の行からタスクを生成 | 2日 | v0.4 |
| AIによる議事録ドラフト生成 | 1週 | v1.1 |

## 10. 外部連携 / MCP

### 10.1 構成

自前 REST API の薄いラッパーとして実装する。UI と AI で別ロジックを持たせない。

```
PostgreSQL → REST API ─┬→ Web UI (Next.js)
                       ├→ MCP Server
                       └→ Discord (Webhook / Interactions)
```

### 10.2 提供ツール

| ツール | 用途 | 権限 |
|---|---|---|
| `list_tasks` | 担当タスクの取得 | read |
| `get_task` | タスク詳細 + 関連ドキュメント | read |
| `search_documents` | 仕様書・ナレッジ・議事録の検索 | read |
| `get_document` | ドキュメント本文取得 | read |
| `start_work` | 作業開始（`agent_session` 生成） | write |
| `update_task_status` | ステータス更新 | write |
| `add_comment` | 進捗コメント投稿 | write |
| `log_work` | 実績工数の記録 | write |
| `end_work` | 作業終了 + サマリ登録 | write |

**認証**: `api_key` テーブルによるエージェント単位のキー。スコープ（read / read_write）と対象プロダクトを制限。

### 10.3 AI作業を確実に記録させる仕組み

エージェントの自発的な報告に依存しない。二重化する。

1. **Claude Code hooks** で `SessionStart` / `SessionEnd` に `start_work` / `end_work` を自動発火
2. **CLAUDE.md に運用規約を記載** — 作業開始時に必ずタスクIDを指定する

`agent_session` の `started_at` / `ended_at` から `work_log` を自動生成する（`source=agent`）。

### 10.4 GitHub 連携

コミットメッセージ内の `PRD-123` 形式を検出してタスクに紐付け、`activity` に記録する。Webhook で受信。

## 11. 非機能要件

### 11.1 セキュリティ

外部基準への準拠要件はない。以下は実利のために設定する水準。

| 項目 | 要件 |
|---|---|
| 通信 | HTTPS。**Caddy が証明書を自動取得・更新**（アプリ側の TLS 実装は不要） |
| パスワード | Argon2id、最小12文字 |
| 2要素認証 | TOTP。全ロールで任意設定（強制しない） |
| セッション | HttpOnly + Secure + SameSite=Lax cookie。`session` テーブルで管理 |
| 招待リンク | 単回利用・72時間有効・ロール固定・発行者による即時失効可能。QRはリンクのラッパーであり強度は同一 |
| 添付ファイル | 拡張子ホワイトリスト、実行可能形式の拒否、サイズ上限 |
| レート制限 | ログイン試行 5回/15分、API 全体にも適用 |
| 連携情報 | Webhook URL・APIキーは暗号化保存。ログ出力禁止 |
| Discord Interactions | Ed25519 署名検証必須 |
| 変更履歴 | 全書き込み操作を `activity` に記録。削除・改変不可 |
| CSP / CSRF | 対策必須 |
| コンテナ公開範囲 | **`127.0.0.1` のみに publish**。外部から直接叩けない状態にする |

`activity` の目的は規程準拠ではなく「変更経緯を追える」「障害時に原因を特定できる」という実利。作り込みは最小限でよいが、記録自体は省略しない（ヒートマップとタイムラインの前提になるため）。

### 11.2 バックアップ

- `pg_dump` 日次自動 + **VPS外**（オブジェクトストレージ等）へ転送
- 添付ファイルボリュームも同様
- 保持: 日次7世代 + 週次4世代 + 月次6世代
- **月1回、リストア手順を実際に実行して検証する**

規程のためではなく、VPS障害で仕様書とタスク履歴が消えるとプロジェクトそのものが止まるため。一人運用だからこそ「動くと思っていたバックアップが動かない」を先に潰す。

### 11.3 可用性・運用

- 単一VPS、冗長化なし
- 目標稼働: 平日 9:00-19:00
- **障害時の復旧手順書を成果物に含める**（属人化の緩和）
- 死活監視 + ディスク使用率アラート

### 11.4 性能

- タスク1万件規模を想定
- かんばん初期表示 1秒以内
- 全文検索 2秒以内

## 12. デプロイ構成

### 12.1 環境

| 項目 | 内容 |
|---|---|
| VPS | 6コア / 8GB / 800GB NVMe SSD |
| 既存の使用メモリ | 約 837MB |
| リバースプロキシ | **Caddy（ホスト側に直接インストール）** |
| 方針 | Docker Compose によるアプリ単位の完全分離 |

### 12.2 コンテナ構成

本ツール専用の Compose ファイルで完結させる。既存アプリとはネットワーク・ボリュームとも共有しない。

| サービス | 内容 |
|---|---|
| `app` | Next.js。`127.0.0.1:3000` に publish |
| `db` | PostgreSQL 16 + pg_bigm。**ホストに publish しない**（Compose 内ネットワークのみ） |

```yaml
name: atlasquarry

services:
  app:
    image: atlasquarry:latest
    container_name: atlasquarry-app
    ports:
      - "127.0.0.1:3000:3000"    # ホストのループバックのみ
    volumes:
      - atlasquarry-attachments:/var/atlasquarry/attachments
    depends_on: [db]
  db:
    build: ./docker/postgres      # pg_bigm 入りのカスタムイメージ
    container_name: atlasquarry-db
    volumes:
      - atlasquarry-db-data:/var/lib/postgresql/data
    # ports は指定しない

volumes:
  atlasquarry-db-data:
  atlasquarry-attachments:
```

### 12.2.1 リソース命名

既存アプリとの衝突を避けるため、全リソースに `atlasquarry` を接頭辞として付ける。
導入前に `docker ps -a` / `docker volume ls` / `docker network ls` で衝突がないことを確認する。

| 用途 | 値 |
|---|---|
| Compose プロジェクト名 | `atlasquarry` |
| イメージ | `atlasquarry:latest` |
| コンテナ | `atlasquarry-app` / `atlasquarry-db` |
| ボリューム | `atlasquarry-db-data` / `atlasquarry-attachments` |
| DB名 | `atlasquarry` |
| サブドメイン | `quarry.example.com` |

### 12.3 PostgreSQL イメージ

公式イメージには pg_bigm が含まれないため、拡張入りのカスタムイメージをビルドする。

```dockerfile
FROM postgres:16
RUN apt-get update && apt-get install -y postgresql-16-pgdg-pg-bigm \
 && rm -rf /var/lib/apt/lists/*
```

パッケージ名はディストリにより異なる。入手できない場合はソースビルドに切り替える。初期化時に `CREATE EXTENSION pg_bigm;` を実行する。

### 12.4 Caddy 設定

ホスト側の Caddyfile にサイトブロックを追加する。証明書は Caddy が自動取得・更新するため、アプリ側で TLS を扱わない。

```
quarry.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

### 12.5 ビルドとデプロイの方針

**VPS 上でビルドしない。**

Next.js の本番ビルドは瞬間的に 2〜4GB のメモリを消費する。既存アプリが稼働中にこれを実行すると、OOM Killer が予期しないプロセスを停止させる恐れがある。

**手順**

1. **ローカル環境でイメージをビルドする**
2. 以下のいずれかで VPS へ転送する
   - コンテナレジストリ経由（`docker push` / `docker pull`）
   - `docker save` でイメージを tar 化 → `scp` で転送 → VPS 上で `docker load`
3. VPS 上では `docker compose up -d` によるコンテナ入れ替えのみを行う

VPS 上でのビルドが避けられない場合に限り、`docker build --memory=3g` でメモリ上限を明示し、swap を 4GB 確保すること。

### 12.6 ボリューム

| ボリューム | 用途 | バックアップ |
|---|---|---|
| `atlasquarry-db-data` | PostgreSQL データ | `pg_dump` で論理バックアップ |
| `atlasquarry-attachments` | 添付ファイル | tar でアーカイブ |

バックアップは `docker run --rm -v <volume>:/data` 方式で吸い出す。分離方針と整合させ、ホスト側のパスに依存させない。

### 12.7 ストレージ抽象化

添付ファイルは VPS ローカル（名前付きボリューム）に保存する。ただし `StorageAdapter` インターフェースを挟み、将来 S3 互換ストレージへ差し替え可能にする。実装コストは半日程度。

### 12.8 メモリ配分の目安

| 用途 | 目安 |
|---|---|
| 既存アプリ | 約 837MB |
| PostgreSQL（新規） | 1GB |
| Next.js | 512MB〜1GB |
| OS・余裕 | 1GB |
| **合計** | **約 4GB（8GB中）** |

ビルドを VPS 上で行わないため、ピーク時のメモリ枯渇リスクは発生しない。
