## 2. 認証

### 2.1 方式

セッション Cookie 方式。JWT は使わない（即時失効ができないため）。

```
ログイン
  → パスワード検証（Argon2id）
  → TOTP が設定されていれば追加検証
  → session テーブルにレコード作成
  → トークンを Cookie にセット
```

### 2.2 Cookie

| 属性 | 値 |
|---|---|
| 名前 | `aq_session` |
| HttpOnly | true |
| Secure | true |
| SameSite | Lax |
| Path | `/` |
| 有効期間 | 30日（`session.expires_at` と一致させる） |

トークンは 32 バイトのランダム値。**DB には SHA-256 ハッシュのみを保存する。**

### 2.3 パスワード

- Argon2id
- 最小12文字
- パラメータ: メモリ 64MB、イテレーション 3、並列度 4（VPS のスペックに合わせて調整可）

### 2.4 TOTP

全ロールで任意設定。強制しない。

- 標準の TOTP（30秒、6桁）
- `actor.totp_secret` は暗号化して保存する
- リカバリコードは v0.1 では実装しない（管理者が手動で解除する運用）

### 2.5 レート制限

| 対象 | 制限 |
|---|---|
| ログイン試行 | 5回 / 15分 / IP+ユーザーID |
| API 全体 | 300回 / 分 / セッション |
| 招待トークンの検証 | 10回 / 時 / IP |

実装は DB カウンタで十分（3名規模）。Redis は使わない。

### 2.6 権限判定

`lib/auth/rbac.ts` に集約する。各所に散らさない。

```ts
type Action =
  | 'request.create' | 'request.triage'
  | 'task.create' | 'task.update' | 'task.delete'
  | 'document.edit' | 'minutes.confirm'
  | 'worklog.viewAll' | 'member.invite'
  | 'activity.viewAll' | 'integration.manage';

function can(actor: Actor, action: Action, resource?: unknown): boolean;
```

条件付き権限（`developer` は自分の工数のみ閲覧、`agent` は自分に割当済のタスクのみ更新）は `resource` 引数で判定する。

**API ハンドラの冒頭で必ず `can()` を通す。** UI 側での非表示は補助であり、権限の実体はサーバー側に置く。

### 2.7 招待

```
発行: ランダム32バイト → SHA-256 を invitation.token_hash に保存
      有効期限 = now + 72h、max_uses = 1、role を固定
受諾: /invite/[token] → ハッシュ照合 → アカウント作成 → used_count++
失効: revoked_at をセット
```

QR は招待 URL をエンコードしたもの。**QR 自体に追加のセキュリティ機能はない**ため、リンクと同じ扱いにする。

## 3. API 設計

### 3.1 規約

- パス: `/api/v1/{resource}` 、`/api/v1/{resource}/{id}`
- メソッド: GET / POST / PATCH / DELETE
- リクエスト・レスポンスとも JSON
- 日時は ISO 8601（UTC）。表示側でローカル時刻に変換する

### 3.2 レスポンス形式

成功:

```json
{ "data": { ... } }
```

一覧:

```json
{ "data": [ ... ], "meta": { "total": 120, "limit": 50, "offset": 0 } }
```

エラー:

```json
{ "error": { "code": "TASK_NOT_FOUND", "message": "タスクが見つかりません", "details": null } }
```

### 3.3 エラーコードと HTTP ステータス

| クラス | HTTP | 用途 |
|---|---|---|
| `ValidationError` | 400 | 入力不正 |
| `UnauthorizedError` | 401 | 未認証 |
| `ForbiddenError` | 403 | 権限不足 |
| `NotFoundError` | 404 | 対象なし |
| `ConflictError` | 409 | 排他ロック衝突、キー重複 |
| `RateLimitError` | 429 | レート制限 |
| `InternalError` | 500 | 想定外 |

`lib/errors.ts` に基底クラス `AppError` を定義し、API 層で一律に変換する。

**500 エラーの `message` に内部情報を含めない。** 詳細はサーバーログにのみ出力する。

### 3.4 バリデーション

入力検証は API 層の入口で行う。ドメイン層は「検証済みの値が来る」前提で書く。

スキーマ定義には zod 等を使ってよい（追加ライブラリの確認対象）。

## 4. ドメインイベントと通知

### 4.1 フロー

```
domain の mutation
  → EventBus に publish（同一トランザクション内）
  → notification レコード作成（Web通知）
  → notification_pref を参照
  → mail / discord 対象なら notification_queue に enqueue
  → worker が非同期で送信
```

**送信そのものはリクエストの中で行わない。** Discord や SMTP が詰まったとき、ツール本体のレスポンスが停止するのを防ぐ。

### 4.2 イベント種別

```ts
type DomainEvent =
  | { type: 'task.assigned'; taskId: string; assigneeId: string }
  | { type: 'task.commented'; taskId: string; commentId: string }
  | { type: 'task.completed'; taskId: string }
  | { type: 'mention'; targetType: string; targetId: string; actorIds: string[] }
  | { type: 'request.created'; requestId: string }
  | { type: 'request.decided'; requestId: string; accepted: boolean }
  | { type: 'task.dueSoon'; taskId: string }
  | { type: 'task.overdue'; taskId: string }
  | { type: 'agent.workCompleted'; sessionId: string };
```

### 4.3 NotifierAdapter

```ts
type NotifyPayload = {
  actorId: string;
  eventType: string;
  title: string;
  body: string;
  url?: string;
};

interface NotifierAdapter {
  readonly channel: 'discord' | 'mail';
  send(payload: NotifyPayload): Promise<void>;
}
```

新しいチャネルを足すときは実装を1つ追加するだけで済むようにする。呼び出し側は具象クラスを知らない。

### 4.4 キューワーカー

DB ベースの簡易キュー。

- `notification_queue` から `status='pending' AND next_retry_at <= now()` を取得
- `FOR UPDATE SKIP LOCKED` で多重処理を防ぐ
- 失敗時は `attempts++`、指数バックオフで `next_retry_at` を設定
- 5回失敗で `status='failed'`

起動方法は Next.js の instrumentation hook で `setInterval` を回す方式でよい（3名規模）。別プロセスは立てない。

## 5. Discord 連携

### 5.1 通知送信

`integration.config_encrypted` から Webhook URL を復号し、POST する。

- **URL をログに出さない**
- メンションは `<@{discord_user_id}>` 形式。`actor_external_id` から解決する
- レート制限（約5req/秒）を考慮し、キューワーカーで間隔を空ける

### 5.2 Interactions エンドポイント

`POST /api/discord/interactions`

**必須の処理順**:

1. `X-Signature-Ed25519` と `X-Signature-Timestamp` ヘッダで Ed25519 署名を検証。失敗なら **401**
2. `type: 1`（PING）なら `{ type: 1 }` を返す
3. それ以外は **3秒以内に応答する**。処理が重い場合は `{ type: 5 }`（deferred）を返し、後から follow-up webhook で結果を送る

署名検証を Next.js の Route Handler で行うため、**リクエストボディを生の文字列で取得する**必要がある。パース済みの JSON では検証できない。

### 5.3 コマンド

| コマンド | 処理 |
|---|---|
| `/request <内容>` | `actor_external_id` からユーザー解決 → `request` 作成（`source='discord_command'`）→ 起票完了を返信 |
| `/decide <内容>` | `decision_note` 作成 |
| `/task <key>` | タスク概要を ephemeral（本人のみ表示）で返信 |

未登録の Discord ユーザーからのコマンドは拒否する。

## 6. アクティビティ記録

### 6.1 実装方針

`domain/activity/recorder.ts` に集約する。

```ts
async function recordActivity(tx: Transaction, params: {
  actorId: string;
  entityType: EntityType;
  entityId: string;
  action: ActivityAction;
  diff?: Record<string, unknown>;
  ip?: string;
  userAgent?: string;
}): Promise<void>;
```

**必ずミューテーションと同一トランザクション内で呼ぶ。** 別トランザクションにすると、本体が成功して記録が失われるケースが生じる。

### 6.2 重み

`app_setting` から取得する。ハードコードしない。

| アクション | 初期値 |
|---|---|
| `complete` | 5 |
| `document.create` / `document.update` | 3 |
| `create` / `update` | 2 |
| `triage` | 2 |
| `comment` | 1 |
| `status_change` | 1 |

`activity.weight` には記録時点の重みを保存する。後から重みを変えても過去のヒートマップが揺れないようにするため。

### 6.3 ヒートマップの集計

```sql
SELECT date_trunc('day', created_at AT TIME ZONE 'Asia/Tokyo')::date AS d,
       SUM(weight) AS score
FROM activity
WHERE created_at >= $1 AND ($2::uuid IS NULL OR actor_id = $2)
GROUP BY d;
```

タイムゾーンに注意。UTC のまま集計すると日付境界がずれる。

表示モードは3種（作業量スコア / 完了タスク数 / 実績工数）。クエリを差し替えるだけで対応する。

## 7. 並び順（position）

### 7.1 方式

`double precision` による中間値挿入。

```ts
const STEP = 1024;

function positionBetween(prev: number | null, next: number | null): number {
  if (prev === null && next === null) return 0;
  if (prev === null) return next! - STEP;
  if (next === null) return prev + STEP;
  return (prev + next) / 2;
}
```

### 7.2 再採番

隣接値の差が `1e-6` を下回ったら、そのリスト全体を `STEP` 間隔で振り直す。

3名規模で発生する可能性は低いが、実装しておくこと。発生してから対応すると、並び順が壊れた状態でユーザーが操作することになる。

## 8. 全文検索

### 8.1 拡張

```sql
CREATE EXTENSION IF NOT EXISTS pg_bigm;
```

### 8.2 インデックス

検索対象カラムに GIN インデックスを張る。

```sql
CREATE INDEX idx_task_title_bigm    ON task    USING gin (title gin_bigm_ops);
CREATE INDEX idx_task_body_bigm     ON task    USING gin (body_md gin_bigm_ops);
CREATE INDEX idx_request_title_bigm ON request USING gin (title gin_bigm_ops);
CREATE INDEX idx_request_body_bigm  ON request USING gin (body_md gin_bigm_ops);
CREATE INDEX idx_document_title_bigm ON document USING gin (title gin_bigm_ops);
CREATE INDEX idx_document_body_bigm  ON document USING gin (body_md gin_bigm_ops);
```

### 8.3 クエリ

3テーブルを UNION ALL で横断する。専用の検索インデックステーブルは作らない（同期ズレの原因になる）。

```sql
SELECT 'task' AS kind, id, key AS ref, title, body_md, updated_at FROM task
  WHERE title LIKE '%' || $1 || '%' OR body_md LIKE '%' || $1 || '%'
UNION ALL
SELECT 'request', id, NULL, title, body_md, created_at FROM request
  WHERE title LIKE '%' || $1 || '%' OR body_md LIKE '%' || $1 || '%'
UNION ALL
SELECT 'document', id, NULL, title, body_md, updated_at FROM document
  WHERE title LIKE '%' || $1 || '%' OR body_md LIKE '%' || $1 || '%'
ORDER BY updated_at DESC
LIMIT 50;
```

pg_bigm は `LIKE '%...%'` を GIN インデックスで高速化する。2文字未満の検索語はインデックスが効かないため、**入力を2文字以上に制限する**。

Drizzle では表現しきれないため、`db/queries/search.ts` に生SQLで置く。

## 9. ドキュメントの排他ロック

リアルタイム共同編集は行わない。

```
編集開始: locked_by = 自分, locked_at = now()
保存    : document_revision に旧本文を退避 → body_md を更新 → ロック解除
放置    : locked_at から30分経過で他者が強制解除可能
```

他者がロック中の場合、編集ボタンを無効化し「◯◯さんが編集中」と表示する。**強制解除には確認ダイアログを挟む。**

保存時に `updated_at` を比較し、取得時と異なれば `ConflictError` を返す。

## 10. ファイル添付

### 10.1 StorageAdapter

```ts
interface StorageAdapter {
  put(key: string, data: Buffer, mimeType: string): Promise<void>;
  get(key: string): Promise<Buffer>;
  delete(key: string): Promise<void>;
  url(key: string): Promise<string>;   // ローカル実装ではアプリ経由の配信URL
}
```

v0.3 では `LocalStorageAdapter`（名前付きボリューム）のみ実装する。S3 互換への差し替えを想定してインターフェースを固定する。

### 10.2 制限

- 拡張子ホワイトリスト方式。実行可能形式（`.exe` `.sh` `.bat` `.js` 等）は拒否
- MIME タイプも検証する（拡張子だけを信用しない）
- 1ファイル 50MB 上限
- 配信時は `Content-Disposition: attachment` と `X-Content-Type-Options: nosniff` を付与する

## 11. MCP サーバー（v1.0）

### 11.1 方針

REST API の薄いラッパーとして実装する。ドメイン層を直接呼ぶ形でもよいが、**UI と別のロジックを持たせない**。

### 11.2 認証

`api_key` テーブルのキーで認証する。

- キーは平文保存しない（SHA-256 ハッシュ）
- `scope` が `read` のキーで write ツールを呼んだら 403
- `product_ids` が指定されていれば、対象外プロダクトへのアクセスを拒否

### 11.3 エージェント作業の記録

```
start_work(task_id) → agent_session 作成、task.status を in_progress に
end_work(summary)   → agent_session 更新、ended_at セット
                    → started_at/ended_at から work_log を自動生成（source='agent'）
```

Claude Code の hooks から `SessionStart` / `SessionEnd` で自動発火させる想定。

## 14. テスト方針

v0.1 では網羅的なテストは書かない。以下に限定する。

| 対象 | 理由 |
|---|---|
| `lib/auth/rbac.ts` | 権限は間違えると影響が大きい |
| `lib/position.ts` | 境界条件でバグが出やすい |
| ステータス遷移のルール | 仕様が固まっている |

UI とAPIの結合テストは、機能が安定してから追加する。
