# AtlasQuarry v0.1 実装スコープと受入基準

**このフェーズのゴール: 3人で実運用を開始できる最小構成。**

機能定義書には v1.1 までの全機能が書かれているが、**本書に記載されたものだけを実装する。**

> **2026-08-01 改訂。** 初版を実装して触ってもらった結果、以下の2点をオーナー判断で変更した。
>
> 1. **要望フロー（F-07 / F-08）を v0.2 から前倒しして v0.1 に含める。**
>    「開発要望をどこから出すのか分からない」という指摘による。要望の受け口が無いと、
>    このツールが何のためにあるのかが利用者に伝わらない。テーブルは既に全て作ってあるため、
>    追加は画面と API のみ。
> 2. **画面上の呼び名を「プロダクト」から「プロジェクト」に変える。**
>    「プロダクトとは何か分からない」という指摘による。DB のテーブル名 `product` は変えない。
>
> あわせて、設定画面（メンバー管理・プロジェクト編集・表示名の変更）を追加した。

## 1. 含むもの

| # | 機能 | 内容 |
|---|---|---|
| F-01 | 認証 | ログイン、ログアウト、セッション管理。TOTP は任意設定 |
| F-02 | プロジェクト・開発項目管理 | CRUD。開発項目の進捗はタスクから自動導出 |
| F-03 | タスクCRUD | 作成、編集、削除、ステータス変更、担当者割当 |
| F-04 | かんばんボード | ドラッグ&ドロップ、フィルタ |
| F-05 | コメント | タスクへのコメント投稿・表示 |
| F-06 | アクティビティ記録 | 全書き込み操作の記録 |
| F-07 | 要望の起票・トリアージ | 誰でも要望を出せる。管理者以上が判断する（**2026-08-01 に前倒し**） |
| F-08 | 要望→タスク変換 | 着手すると決めた要望をタスクにする（**2026-08-01 に前倒し**） |
| − | 設定 | メンバーの名前・権限変更、プロジェクト編集・削除、ステータス等の表示名変更 |

初期ユーザーはシードスクリプトで作成する。招待機能（F-10）は v0.2。

以下は**テーブル定義以外を実装しない。** 画面・API・ロジックを先回りして作らないこと。

- 通知（F-09）、メール送信
- 招待リンク・QR（F-10）
- Discord 連携（F-22a〜d）
- ドキュメント・議事録（F-11 / F-23）
- 全文検索（F-12）
- 添付ファイル（F-13）
- ガントチャート（F-14）
- カレンダー（F-15）
- ヒートマップ（F-16）
- 工数算出（F-17）
- MCPサーバー（F-18）
- エクスポート（F-19 / F-21）
- アクティビティ閲覧画面（F-20）
- ラベル機能のUI（テーブルは作るが画面は v0.2 以降）

**テーブルは全て作る。** 後からのマイグレーションを減らすため、DB設計書 §3 の全テーブルを初回マイグレーションに含める。

## 3. 画面

ナビゲーションは **ホーム / 要望 / タスク / プロジェクト / 設定** の5本。
機能をそのまま並べるのではなく、**利用者が「次に何をするか」で並べる。**

| # | パス | 内容 |
|---|---|---|
| S-01 | `/login` | メール + パスワード。TOTP 設定済みなら追加入力 |
| S-02 | `/` | ホーム。役割ごとに出し分ける（下記） |
| S-10 | `/requests` | 要望一覧。ステータス別タブ。「要望を出す」が主操作 |
| S-11 | `/requests/[id]` | 要望詳細。判断（検討中 / 着手する / 見送る）とタスク変換 |
| S-05 | `/tasks` | タスク。**一覧表示とかんばん表示を切り替える**（別画面にしない） |
| S-06 | `/tasks/[key]` | タスク詳細。コメント、タイムライン |
| S-03 | `/projects` | プロジェクト一覧。進捗率表示 |
| S-04 | `/projects/[id]` | 開発項目一覧。進捗バー |
| − | `/settings` | 設定の入口。下記4つへ分岐 |
| − | `/settings/profile` | 自分の設定。名前・パスワード・2要素認証 |
| − | `/settings/members` | メンバーの名前・権限変更、利用停止 |
| − | `/settings/projects` | プロジェクトの編集・削除 |
| − | `/settings/labels` | ステータス・優先度の表示名変更 |

**全画面がモバイルで実用的に操作できること。**

### ホームの出し分け

| 役割 | 上から順に出すもの |
|---|---|
| 経営者 | 判断待ちの要望 / 全体の進捗 / 期限超過 |
| 管理者 | 判断待ちの要望 / 期限超過 / 自分のタスク |
| 開発者 | 自分のタスク / 期限超過 / 着手が決まった要望 |

### 空状態

**「ありません」で終わらせない。** 何のための場所かを1行で説明し、次の操作へのボタンを置く。
初めて開いた人が、説明書なしで最初の1件を作れること。

## 4. API

`/api/v1` 配下。認証は全エンドポイントで必須。

```
POST   /auth/login
POST   /auth/logout
GET    /auth/me
POST   /auth/totp/setup
POST   /auth/totp/verify
DELETE /auth/totp

GET    /products
POST   /products
GET    /products/:id
PATCH  /products/:id
DELETE /products/:id

GET    /products/:id/features
POST   /features
PATCH  /features/:id
DELETE /features/:id
PATCH  /features/:id/position

GET    /tasks                      ?productId= &status= &assigneeId= &featureId=
POST   /tasks
GET    /tasks/:key
PATCH  /tasks/:id
DELETE /tasks/:id
PATCH  /tasks/:id/position         かんばんのDnD用。status と position を同時更新

GET    /tasks/:id/comments
POST   /tasks/:id/comments
DELETE /comments/:id

GET    /tasks/:id/activity
GET    /activity                   ?limit= &offset=

GET    /requests                   ?status=
POST   /requests                   要望を出す
GET    /requests/:id
PATCH  /requests/:id               トリアージ（status / reject_reason）
POST   /requests/:id/convert       タスクに変換（F-08）

GET    /actors                     メンバー一覧（担当者選択用）
PATCH  /actors/me                  自分の名前・パスワード
PATCH  /actors/:id                 メンバーの名前・権限・利用停止（管理者以上）

GET    /settings/labels            ステータス・優先度の表示名
PATCH  /settings/labels
```

**API のパスは `products` のまま**（DB のテーブル名に合わせる）。画面上の呼び名だけ
「プロジェクト」にする。URL は `/projects` を使い、内部で products API を叩く。

## 5. 受入基準

実装完了の判定に使う。全項目を満たすこと。

### 5.1 認証

- [ ] 正しいメール・パスワードでログインでき、Cookie が発行される
- [ ] 誤ったパスワードでログインできず、どちらが誤りかを示さないメッセージが返る
- [ ] 未認証で `/` にアクセスすると `/login` にリダイレクトされる
- [ ] ログアウトすると `session` レコードが削除され、以降アクセスできない
- [ ] ログイン失敗を5回繰り返すと15分間ロックされる
- [ ] TOTP を設定でき、設定後はログイン時に6桁コードを要求される
- [ ] TOTP 未設定のユーザーは6桁コードを要求されない
- [ ] `session` トークンが DB に平文で保存されていない

### 5.2 プロダクト・開発項目

- [ ] プロダクトを作成でき、`key` が `^[A-Z][A-Z0-9]{1,9}$` で検証される
- [ ] 重複する `key` でプロダクトを作成できない
- [ ] 開発項目を作成でき、プロダクトに紐づく
- [ ] 開発項目の進捗率が「完了タスク数 / 総タスク数」で表示される
- [ ] 開発項目に `start_date` / `due_date` が未設定の場合、配下タスクの MIN / MAX が表示される
- [ ] 開発項目に日付が設定されている場合、そちらが優先される
- [ ] タスクが0件の開発項目で進捗率がエラーにならない

### 5.3 タスク

- [ ] タスクを作成すると `{product.key}-{連番}` 形式のキーが採番される
- [ ] 同時に複数タスクを作成してもキーが重複しない
- [ ] 開発項目を指定せずにタスクを作成できる（`feature_id` は nullable）
- [ ] `start_date > due_date` のタスクを保存できない
- [ ] ステータスを `done` にすると `completed_at` がセットされる
- [ ] `done` から他のステータスに戻すと `completed_at` が null に戻る
- [ ] サブタスク（`parent_task_id`）を作成できる
- [ ] 権限のないロールがタスクを削除できない

### 5.4 かんばん

- [ ] ステータスごとの列にタスクが表示される
- [ ] カードをドラッグして別の列に移動でき、ステータスが更新される
- [ ] 同一列内で並び替えでき、`position` が更新される
- [ ] 並び替え時に他のカードの `position` が UPDATE されない（中間値挿入）
- [ ] 担当者・優先度・開発項目でフィルタできる
- [ ] **スマホでドラッグ&ドロップが動作する**（タッチイベント対応）
- [ ] タスク0件の列で表示が崩れない

### 5.5 コメント

- [ ] タスク詳細からコメントを投稿できる
- [ ] Markdown がレンダリングされる
- [ ] 投稿者本人と `manager` 以上が削除できる
- [ ] 空のコメントを投稿できない

### 5.9 要望（F-07 / F-08）

- [ ] 全ロール（`requester` を含む）が要望を出せる
- [ ] `agent` は要望を出せない
- [ ] 要望はステータス別（受付中 / 検討中 / 着手する / 見送る / 完了）に絞り込める
- [ ] `developer` 以上がトリアージできる
- [ ] 見送る場合は理由が必須（理由なしで保存できない）
- [ ] 「着手する」にした要望をタスクに変換でき、`converted_task_id` が埋まる
- [ ] 変換済みの要望を二重に変換できない
- [ ] 変換で作られたタスクから、元の要望へ辿れる
- [ ] 要望の起票・トリアージ・変換が `activity` に記録される

### 5.10 設定

- [ ] `manager` 以上がメンバーの名前と権限を変更できる
- [ ] `developer` はメンバーの権限を変更できない
- [ ] **自分自身の権限を下げられない**（最後の `owner` が居なくなる事故を防ぐ）
- [ ] メンバーを利用停止にでき、停止後はログインできない
- [ ] ステータス・優先度の表示名を変更でき、変更が全画面に反映される
- [ ] 表示名を空にした場合は既定値に戻る

### 5.11 分かりやすさ

- [ ] **画面に「プロダクト」という語が出ない**（すべて「プロジェクト」）
- [ ] DB 上の英語名（`feature` / `request` / `actor` 等）が画面に出ない
- [ ] 各画面の空状態が、何のための場所かの説明と次の操作へのボタンを持つ
- [ ] 初めてログインした人が、説明書なしで「要望を出す」に辿り着ける

### 5.6 アクティビティ

- [ ] タスクの作成・更新・ステータス変更・完了・削除が `activity` に記録される
- [ ] コメント投稿が記録される
- [ ] プロジェクト・開発項目の作成・更新が記録される
- [ ] `activity.weight` に記録時点の重みが保存されている
- [ ] タスク詳細にタイムラインとして時系列表示される
- [ ] **ミューテーションが失敗した場合、`activity` にも記録されない**（同一トランザクション）
- [ ] `activity` に対する UPDATE / DELETE のコードが存在しない

### 5.7 権限

- [ ] `can()` を経由せずに権限判定しているAPIハンドラが存在しない
- [ ] `developer` がタスクを削除できない
- [ ] `owner` / `manager` がタスクを削除できる
- [ ] UI で非表示にしている操作を、API 直叩きでも実行できない

### 5.8 非機能

- [ ] `tsc --noEmit` が通る
- [ ] 本番ビルドが通る
- [ ] Docker Compose で起動し、`127.0.0.1:3000` でのみ待ち受ける
- [ ] `db` サービスがホストにポートを publish していない
- [ ] ログに秘匿情報（トークン、パスワードハッシュ、TOTPシークレット）が出力されない
- [ ] `localStorage` / `sessionStorage` を使用していない
- [ ] 全画面がスマホ幅（375px）で横スクロールなしに表示される
- [ ] ローディング・エラー・空状態が全画面に実装されている
- [ ] `.env` がリポジトリに含まれていない

## 6. 完了の定義

以下が揃った時点で v0.1 完了とする。

1. 上記の受入基準を全て満たす
2. ローカルでイメージをビルドし、VPS へ転送して起動できる
3. Caddy 経由で HTTPS アクセスできる
4. `scripts/backup.sh` が動作し、**リストアが成功することを実際に確認済み**
5. 3人分のアカウントがシードされ、実際にログインできる

## 7. 実装順の目安

依存関係を考慮した推奨順序。

1. DB スキーマ（全テーブル）とマイグレーション
2. Docker 環境（`compose.yml`、pg_bigm 入り Dockerfile）
3. `lib/errors.ts`、`lib/position.ts`、`lib/auth/*`
4. 認証（F-01）＋ シードスクリプト
5. `domain/activity/recorder.ts`
6. プロダクト・開発項目（F-02）
7. タスク CRUD（F-03）
8. かんばん（F-04）
9. コメント（F-05）
10. ダッシュボード
11. バックアップ・リストアスクリプト

**3 と 5 を先に作ること。** 後から挟むと、既に書いたコードを全て書き直すことになる。
