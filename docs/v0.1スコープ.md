# AtlasQuarry v0.1 実装スコープと受入基準

**このフェーズのゴール: 3人で実運用を開始できる最小構成。**

機能定義書には v1.1 までの全機能が書かれているが、**本書に記載されたものだけを実装する。**

> **2026-08-01 改訂。** 初版を実装して触ってもらった結果、以下の2点をオーナー判断で変更した。
>
> 1. **要望フロー（F-07 / F-08）を v0.2 から前倒しして v0.1 に含める。**
>    「開発要望をどこから出すのか分からない」という指摘による。要望の受け口が無いと、
>    このツールが何のためにあるのかが利用者に伝わらない。テーブルは既に全て作ってあるため、
>    追加は画面と API のみ。
> 2. **画面上の呼び名を「プロダクト」から「プロジェクト」に変える。**
>    「プロダクトとは何か分からない」という指摘による。DB のテーブル名 `product` は変えない。
>
> 3. **ガントチャート（F-14）を v0.4 から前倒しして v0.1 に含める。** ただし帯の表示までとし、
>    依存線は v0.4 のまま据え置く（D-05 のとおり依存関係の入力は手動・任意のため、
>    先に線だけ作っても入力する動機がない）。
>
> 4. **スタイルを Tailwind CSS v4 + shadcn/ui に置き換える。** 手書きCSSは撤去した。
>    「モダンな技術を使ってよい」というオーナー判断による。
>    ~~ホーム画面には**進行中プロジェクトのガント**を載せ~~
>    → **2026-08-02 に取り下げ。ホームからガントを外した**（5.13 を参照）。
>
> 5. **ホームを「状況を報告する画面」から「次の一手を出す画面」に作り替える。**（2026-08-02）
>    「AI感のないものにして」という指摘への対応。3指標の帯とガントをやめ、最上部を
>    役割ごとの「いま動かすこと」1ブロックにした。タスク画面は既定を「自分の担当」に絞り、
>    絞り込みは畳んだ。**画面の構成の変更のみで、機能の追加・削除はしていない。**
>
> あわせて、設定画面（メンバー管理・プロジェクト編集・表示名の変更）を追加した。

## 3. 画面

スマホの下部タブは **プロジェクト / 今日 / 予定 / 要望** の4本。**左端がプロジェクト。**
機能をそのまま並べるのではなく、**利用者が「次に何をするか」で並べる。**

> **2026-08-02 変更（3回目）：プロジェクトを起点にした。**
> 「プロジェクトが大枠で全ての起点なのに、ホームからアクセスできない上に、
> ドックも右端で重要感がない」との指摘。**下部タブの左端＝アプリの基点**として
> 読まれるので、そこにプロジェクトを置き、`/` をプロジェクト一覧にした。
> 「今日」は個人が自分の作業を処理する2番目の面（`/today`）に下げた。
>
> **タスクのタブは廃止。** タスクは必ずプロジェクトに属するので、全体のタブにすると
> 案件の文脈が切れる。一覧とかんばんはプロジェクトの中の見方にした。
>
> **プロジェクトホームを `概要 / タスク / 予定` の3つに固定した。**
> 概要には遅れ・今日まで・未割当の数を出し、押すとそのタスクへ行く。
>
> **どの画面からもプロジェクトへ戻れるようにした。** タスク詳細の戻り先を
> 「← プロジェクト名」に、要望詳細・予定・今日の各行にもプロジェクトへのリンクを置いた。
> それまでは今日・タスク詳細・予定・要望詳細のどれからもプロジェクト詳細へ到達できなかった。
>
> **2026-08-02 変更（2回目）：ガントを「予定」としてタブに昇格させた。**
> 「ガントチャートを見るためにいろんなところを開いて探さないといけない」との指摘。
> プロジェクト → 詳細 → 予定の札、と3つ辿る必要があった。
> **初期表示は全プロジェクト。** 経営者と上司が日常的に見るものなので入口に置く。
>
> **どの画面からも押せる「＋」を右下に常設した。** 追加するのにまず正しい画面へ
> 移動する必要があった。押した画面の文脈（プロジェクト・まとまり）を引き継ぐ。
>
> **2026-08-02 変更。** もとは「ホーム」を含む5本だった。
> 「ホーム」は何が置いてある場所かを名前が説明しておらず、入口がダッシュボードだと
> 作業を始める前に読む時間が要る。**「今日」に置き換え、自分がいま動かすものだけを出す。**
> **設定はタブから外した**（毎日の仕事の流れに入っていない）。上部の氏名から入る。
> ログアウトは設定画面の最下部へ移した。

**全画面がモバイルで実用的に操作できること。**

### 「今日」に出すもの（2026-08-02 変更）

上から順に固定する。役割で並びを変えるのはやめた。

1. **今日やる** … 自分の担当のうち、期限を過ぎたもの → 今日まで → それ以外。
   先頭の1件だけを大きく出し、理由（期限を過ぎています／今日までです）を添える
2. **あなたの判断待ち** … 判断できる役割のときだけ。**最上段には置かない**
   （常に一番上だと「一日の作業」より「滞留の警告」が入口を支配する）
3. **直近の節目** … 期限超過・次の期限・日程未定

### 空状態

**「ありません」で終わらせない。** 何のための場所かを1行で説明し、次の操作へのボタンを置く。
初めて開いた人が、説明書なしで最初の1件を作れること。

## 5. 受入基準

実装完了の判定に使う。全項目を満たすこと。

### 5.1 認証

- [ ] 正しいメール・パスワードでログインでき、Cookie が発行される
- [ ] 誤ったパスワードでログインできず、どちらが誤りかを示さないメッセージが返る
- [ ] 未認証で `/` にアクセスすると `/login` にリダイレクトされる
- [ ] ログアウトすると `session` レコードが削除され、以降アクセスできない
- [ ] ログイン失敗を5回繰り返すと15分間ロックされる
- [ ] TOTP を設定でき、設定後はログイン時に6桁コードを要求される
- [ ] TOTP 未設定のユーザーは6桁コードを要求されない
- [ ] `session` トークンが DB に平文で保存されていない

#### 自己登録（2026-08-09 変更）

ログイン画面から、ユーザーIDとパスワードだけで登録できる。登録された利用者の役割は
**必ず `manager`（管理者）**で、登録直後からタスク・プロジェクト・要望・メンバー管理を行える。

- [ ] ユーザーIDは必須・空白不可・重複不可
- [ ] 登録された利用者の役割は**必ず `manager`（管理者）**
- [ ] 登録しても**自動ログインしない**
- [ ] **既存のユーザーIDの場合は重複を知らせ、別のIDを選べる**
- [ ] 既存アカウントの内容を、登録で上書きできない
- [ ] 利用停止済みのアカウントを、登録で復活させられない
- [ ] 登録の試行は **IP 単位で 15分5回**まで。ログインの (IP, ユーザーID) ロックとは別のキーで数える
- [ ] アカウントの作成が `activity`（`entity_type = 'actor'`）に記録される

### 5.2 プロジェクト・まとまり

- [ ] プロジェクトを作成できる。**`key`（タスク番号の記号）は入力させず、サーバーが
      `P1` `P2` … と採番する**（2026-08-02 変更。決める理由も基準も利用者に無いため）
- [ ] 採番された `key` は `^[A-Z][A-Z0-9]{1,9}$` を満たし、重複しない
- [ ] **`key` は画面に出さない。** タスクの行にはプロジェクトの**名前**を出す
- [ ] **まとまり**（＝子タスクを持つタスク）の進捗が「完了した子 / 子の総数」で表示される
- [ ] まとまりに日付が入っていなければ、子の開始日 MIN / 期限 MAX から導出される
- [ ] まとまりに日付が入っていれば、そちらが優先される
- [ ] 子が0件のタスクは、まとまりとして扱われない（普通のタスクとして並ぶ）
- [ ] **階層は1段まで**。子の下にさらに足す導線を出さない

> **2026-08-02 変更：開発項目（feature）を画面から外した。**
>
> プロジェクトの下に開発項目があり、**しかも開発項目に入らないタスクも許していた**ので、
> 構造そのものが例外を含んでいた（「これは開発項目か、タスクか」を毎回判定させられる）。
> オーナーから「開発項目とタスクの関係がわかりにくすぎる」との指摘。
>
> 代わりに、既にある親子関係（`parent_task_id`）を使い、**画面では「まとまり」と呼ぶ**。
> 「親タスク」という技術用語は出さない。Jira / Backlog の親子を、
> Asana / Todoist 並みに軽く見せる形（codex に既存製品と比較させたうえで決めた）。
>
> **`feature` テーブルと API は残している**（データも消していない）。
> 既存の開発項目は `scripts/features-to-groups.mjs` でまとまり（親タスク）へ移した。
> 画面・フォーム・絞り込みからは全て外した。

### 5.3 タスク

- [ ] タスクを作成すると `{product.key}-{連番}` 形式のキーが採番される
- [ ] 同時に複数タスクを作成してもキーが重複しない
- [ ] 開発項目を指定せずにタスクを作成できる（`feature_id` は nullable）
- [ ] `start_date > due_date` のタスクを保存できない
- [ ] ステータスを `done` にすると `completed_at` がセットされる
- [ ] `done` から他のステータスに戻すと `completed_at` が null に戻る
- [ ] サブタスク（`parent_task_id`）を作成できる
- [ ] 権限のないロールがタスクを削除できない

### 5.4 かんばん

- [ ] ステータスごとの列にタスクが表示される
- [ ] カードをドラッグして別の列に移動でき、ステータスが更新される
- [ ] 同一列内で並び替えでき、`position` が更新される
- [ ] 並び替え時に他のカードの `position` が UPDATE されない（中間値挿入）
- [ ] 担当者・優先度・開発項目でフィルタできる
- [ ] **スマホでドラッグ&ドロップが動作する**（タッチイベント対応）
- [ ] タスク0件の列で表示が崩れない

### 5.5 コメント

- [ ] タスク詳細からコメントを投稿できる
- [ ] Markdown がレンダリングされる
- [ ] 投稿者本人と `manager` 以上が削除できる
- [ ] 空のコメントを投稿できない

### 5.9 要望（F-07 / F-08）

### 5.x タスクの作成（2026-08-02 追記）

- [ ] タスクは**作成時に、作成元のプロジェクトへ所属する**。プロジェクト詳細や
      開発項目から「タスクを追加」を押したときは、そのプロジェクトが埋まった状態で開く
- [ ] 文脈が無いときは、表示順の先頭のプロジェクトを既定にする
- [ ] 必須の入力は**タスク名の1行だけ**。担当・期限・開発項目は後から足せる

> **v0.1 では次を作らない。**
>
> - **「未整理」プロジェクト**（Todoist の Inbox にあたる、どこにも属さないタスクの受け皿）。
>   プロジェクトが3つ（当面5〜10）の規模では、選ぶ負担より運用場所を増やす負担のほうが大きい。
>   タスクは必ず1つのプロジェクトに属する、というモデルを保つ。
> - **利用者ごとの「最後に使ったプロジェクト」の記憶。** ブラウザストレージは
>   CLAUDE.md で禁止しており、`app_setting` は全体設定なので個人別の値を置けない
>   （3人が互いの既定を上書きしてしまう）。正しくやるには利用者別の保存先が要るため、
>   v0.1 の範囲外とする。
>
> 未整理を採るのは、**プロジェクトが10件前後を超え、作成時に正しいプロジェクトを
> 選べない事例が続けて出たとき**。そのときはキーの恒久化・移管・各集計からの除外を
> あわせて仕様にする。

### 5.13 ホーム

- [ ] ログイン直後の最上段が、**自分が今日やること**（先頭1件を大きく、理由つき）
- [ ] 判断待ちの要望は、判断できる役割にだけ、**今日やることの次に**出る
- [ ] 予定は「直近の節目」として、期限超過・次の期限・日程未定の短い一覧で出る

> **2026-08-02 変更。** もとは「進行中プロジェクトのガントがホームに出る」「日付が入っている
> タスクが1件も無いプロジェクトはホームのガントに出さない」を受入基準にしていた。
> **ホームからガントを外したので取り下げる。** ガントはスマホでは横スクロールが前提になり、
> 「今日へ」のような操作説明も要る。計画を調整するときの道具であって、毎日開くたびに
> 読むものではない、という判断による（オーナーの「AI感のないものにして」への対応の一環）。
> **ガントそのものは残っている**（S-07 / `/projects/[id]?view=gantt`）。F-14 の受入基準（5.12）は
> そのまま有効。
